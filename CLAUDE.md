# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Arduino sketch for an ESP32-S3-WROOM-1 (N16R8) that plays a looping RGB565
animation on a 1.3" 240×240 ST7789 IPS TFT via the `TFT_eSPI` library. A
beam-splitting cube in front of the display turns the 2D loop into a
pseudo-holographic effect. There is no firmware logic beyond decode-free
frame playback — frames are pre-baked into `gif_frames.h`.

## Build / flash

There is no PlatformIO or Makefile — this is an Arduino IDE project.

1. Install the [TFT_eSPI](https://github.com/Bodmer/TFT_eSPI) library.
2. **Apply `User_Setup.h`**: TFT_eSPI is configured by the copy of `User_Setup.h`
   inside the *library* folder, not the one in this repo. The repo's
   `User_Setup.h` is the source of truth for pin/driver config; its contents must
   be copied into the installed library (or referenced via `User_Setup_Select.h`)
   or the display will not work. This is the #1 setup gotcha.
3. Open `HoloCube3D-main.ino`, keep `gif_frames.h` in the same folder.
4. Select an ESP32-S3 board and upload.

No automated tests exist.

## Hardware config (from `User_Setup.h`)

- Driver `ST7789_DRIVER`, 240×240, `TFT_RGB_ORDER TFT_BGR`
- HSPI port (`USE_HSPI_PORT`), `SPI_FREQUENCY 27000000`
- Pins: `TFT_MOSI 11`, `TFT_SCLK 12`, `TFT_MISO 13`, `TFT_CS -1`, `TFT_DC 2`, `TFT_RST 4`

## Frame pipeline (the core architecture)

`gif-split.py` (offline, on a PC) → `gif_frames.h` (committed) → flashed to PROGMEM → drawn in `loop()`.

- **`gif_frames.h`** is auto-generated. It defines `FRAME_COUNT`, `FRAME_WIDTH`,
  `FRAME_HEIGHT`, one `const uint16_t frame_NNN[] PROGMEM` array per frame, and a
  `const uint16_t* const frames[FRAME_COUNT] PROGMEM` pointer table at the end.
- **`HoloCube3D-main.ino`** loops over `frames[]`, reads each frame pointer out of
  PROGMEM with `pgm_read_ptr`, `memcpy_P`s the frame into a RAM buffer
  (`frameBuf`), and pushes it with `setAddrWindow` + `pushPixels`. `FRAME_DELAY`
  (ms) sets the frame rate (~24 fps at 42 ms).
- Both the frame arrays and the pointer table live in flash; only one frame
  (`FRAME_WIDTH*FRAME_HEIGHT*2` bytes) is ever in RAM at a time.

### Known inconsistencies to be aware of before editing

- **`gif-split.py` does not produce `gif_frames.h`.** The committed `gif-split.py`
  writes one `frame_NNN.h` per frame and does **not** emit `FRAME_COUNT`/dimensions
  or the `frames[]` pointer table. `gif_frames.h` was generated by a separate
  "GIF→C Array Splitter" tool (see its header comment). If you regenerate frames,
  you must also reconstruct the single-header format the sketch expects, or rewrite
  `gif-split.py` to emit it.
- **Byte-swap mismatch.** `gif-split.py` byte-swaps each RGB565 value, but the
  sketch calls `tft.setSwapBytes(false)`. If you change the generator's swap
  behavior, keep it consistent with `setSwapBytes` in the sketch (one side must do
  the swap, not both, not neither). Wrong colors / red-blue swap usually trace to
  this or to `TFT_RGB_ORDER`.

## Adding / replacing the animation

The animation is entirely determined by `gif_frames.h`. To change it, regenerate
that header (matching the format above: per-frame PROGMEM arrays + a `frames[]`
table + the three `#define`s) and re-flash. No `.ino` changes are needed unless
frame size or timing changes.
